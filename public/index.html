Browser demo — attestation “none”. A browser passkey is not the attested, device-bound credential a native app produces. This page demonstrates the ceremony, not the attestation.

Passkey — browser ceremony demo

Registration and login against the reference server’s demo API at /demo/api, run entirely from this page. Every request and response is printed below so the ceremony can be watched step by step.

What this page can and cannot show

It can show: the full WebAuthn ceremony — the server issuing a challenge, the platform authenticator creating a credential under biometric/PIN user verification, the signed response travelling back, and the server verifying the signature against the challenge, the relying-party id and the origin.

It cannot show attestation. Consumer platform authenticators reached through a browser (iCloud Keychain, Google Password Manager, Windows Hello) return attestation statement format none, no matter that the server asks for attestation: "direct". There is no certificate chain, no hardware statement, and nothing that proves which app or which key store produced the key. Such a credential is stored here with attested=false.

Only a native app can produce the attested credential. In the app the key is generated in the iOS Secure Enclave or in Android StrongBox/TEE, is biometric-gated by the OS, and is hardware-attested: Android emits attestation format android-key with a certificate chain up to the Google hardware attestation root; iOS emits packed self-attestation plus an Apple App Attest object bound to the same credential. App identity is proven by that attestation — not by Associated Domains, apple-app-site-association or assetlinks.json. This host does serve both of those files, at /.well-known/apple-app-site-association and /.well-known/assetlinks.json, but they belong to the other path: they let iCloud Keychain and Google Password Manager hold a platform passkey for this domain — one that syncs across the user’s devices and returns attestation none, i.e. BSI trust level normal. The attested, device-bound design needs no domain association at all. It is the attestation, and only the attestation, that carries a credential from normal to substantiell, and it is not reachable from a browser.

Consequence for this demo: the credential you are about to create would be rejected by the strict verifier. The endpoints under <basePath>/rest/authentication/passkey/* (basePath defaults to /api) run with attestationPolicy=strict and require an accepted attestation format, the app’s own AAGUID, and a device-bound (non-synced) credential. The /demo/api/* endpoints exist only under attestationPolicy=demo, purely so the ceremony can complete in a browser. After each ceremony this page shows exactly which production rules the browser credential fails.
